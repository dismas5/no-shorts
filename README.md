# Local Blocklist

Локальное расширение для блокировки доменов, разделов и точных страниц. Начальный список **пуст**. Новые сайты добавляются в настройках без изменения кода и пересборки. Расширение не определяет тип контента по названию, длительности видео или картинке: правило всегда задаёт реальный домен и, при необходимости, путь.

Проект содержит TypeScript-исходники без UI-фреймворка, сборку JavaScript, тесты, Firefox-пакет и ресурсы Safari Web Extension. Сервер, прокси, сертификаты и системная служба для работы расширения не нужны.

**Статус проверки:** здесь выполнены автоматические проверки логики/DOM, сборка и Mozilla lint. Настоящее установленное расширение в Firefox и Safari в этой среде не проверено: запуск браузера и loopback-сервера ограничены песочницей. Safari-приложения требуют Mac/Xcode. Это не утверждение о пройденной проверке на устройствах. Подробный [отчёт](docs/VERIFICATION.md), [сценарии](docs/TESTING.md) и [чек-лист Safari](docs/SAFARI-CHECKLIST.md).

## Окружение и быстрый старт

Разработка выполнена на Ubuntu 22.04.5 x86_64, Node.js 22.16.0 и npm 11.7.0. Цели: Firefox Desktop **140+** на Windows 10, Ubuntu 24.04, macOS; Safari **18+** на macOS и Safari в **iOS 18**. Firefox на iOS не поддерживается. Windows/Ubuntu 24.04/macOS не проверялись на настоящих устройствах. API-порог большинства функций Firefox — 128; минимум пакета 140 выбран также для декларации отсутствия сбора данных Mozilla. Android не входит в проверенную матрицу.

Установите Node.js 22 LTS с npm. Все прямые зависимости закреплены точными версиями; полное дерево — `package-lock.json`. Runtime-зависимостей нет. `.npmrc` отключает lifecycle-скрипты зависимостей; esbuild использует закреплённый платформенный optional package, поэтому не используйте `--omit=optional`. TypeScript, esbuild, web-ext и LinkeDOM используются только при разработке.

```bash
npm ci
npm run check
npm run package
```

`check` выполняет строгую проверку типов, автоматические тесты, обе сборки, аудит пакетов и `web-ext lint --warnings-as-errors`. Доступ к npm нужен для первой установки инструментов. Никакие загрузки зависимостей не включаются в работу расширения.

`npm run package` сохраняет Safari ZIP в `artifacts/safari/`. Firefox XPI, общий архив исходников и `SHA256SUMS` находятся в `artifacts/`. Пути в `SHA256SUMS` отсчитываются от `artifacts/`, включая подпапку Safari.

Для загрузки на MacBook используйте постоянный путь `artifacts/safari/local-blocklist-latest-safari-webextension.zip`. Это относительная символическая ссылка на ZIP текущей упакованной версии. После успешного `npm run package` ссылка обновляется автоматически и атомарно; предыдущие версионные архивы сохраняются. В `SHA256SUMS` указаны версионные файлы. Правило деплоя закреплено в [AGENTS.md](AGENTS.md).

| Команда | Результат |
| --- | --- |
| `npm run typecheck` | строгий TypeScript без генерации файлов |
| `npm test` | чистые функции, координатор, ошибки API и поведение DOM |

Тестовый runner использует `--experimental-test-isolation=none` Node 22, чтобы в ограниченных средах тесты исполнялись непосредственно в одном процессе. В выводе перечислены отдельные тесты, а не только файлы.

## Установка Firefox

### Временная разработка

```bash
npm run dev:firefox
# При нестандартном пути к браузеру:
npx web-ext run --source-dir dist/firefox --firefox /путь/к/firefox
```

Или откройте `about:debugging#/runtime/this-firefox` → «Загрузить временное дополнение» → `dist/firefox/manifest.json`. Откройте настройки через значок Local Blocklist на панели; значок может находиться в меню расширений. Временная установка действует до завершения Firefox. Новый временный профиль web-ext не содержит ваших правил.

На Linux для повторных запусков с автоматической временной загрузкой аддона:

```bash
npm run start:firefox
# Необязательная начальная страница:
npm run start:firefox -- https://www.youtube.com/
# При нестандартном пути:
FIREFOX_BIN=/путь/к/firefox npm run start:firefox
```

Запускатель каждый раз собирает расширение и открывает Firefox с отдельным сохраняемым профилем `build/firefox-profile`. Настроенные правила сохраняются между запусками; при первом запуске список пуст. Правила из другого профиля перенесите JSON-экспортом/импортом и заново выдайте доступ к сайтам. Для загрузки аддона каждый раз запускайте эту команду: обычный значок Firefox её не вызывает. Одновременный повторный запуск скрипта блокируется. Не удаляйте `build/firefox-profile`, если нужны его данные; перед очисткой `build/` экспортируйте правила.

**Это профиль для разработки.** `web-ext --keep-profile-changes` включает отладочный доступ без подтверждения соединений и меняет настройки обновлений и проверки подписей. Не используйте основной профиль и не рассматривайте этот способ как более безопасную замену подписи для повседневного браузера. Запускатель использует только свой профиль, не настраивает системный автозапуск и не меняет обычные ярлыки Firefox. См. [предупреждение Mozilla](https://extensionworkshop.com/documentation/develop/getting-started-with-web-ext/#keep-profile-changes).

### Постоянная установка

Обычный Firefox требует **подпись Mozilla**. Файл `artifacts/local-blocklist-1.0.0-firefox-unsigned.xpi` не подписан; обычный Release Firefox не установит его постоянно.

Для личного использования можно отправить пакет на **unlisted-подпись**, без публичного листинга. Исходники и пакет всё равно передаются Mozilla и подлежат её правилам. Создайте AMO developer account и получите JWT credentials; не помещайте их в репозиторий. Поменяйте ID в `scripts/build.mjs`, если уже зарегистрировали другой ID. После первой регистрации сохраняйте тот же ID при обновлениях.

```bash
npm run check
npx web-ext sign --source-dir dist/firefox --artifacts-dir artifacts/signed \
  --channel=unlisted --api-key="$AMO_JWT_ISSUER" --api-secret="$AMO_JWT_SECRET"
```

Можно загрузить ZIP/XPI через AMO Developer Hub и выбрать самостоятельное распространение. При запросе исходников приложите source ZIP, lockfile и инструкции `npm ci && npm run build`. Подписанный XPI установите через `about:addons` → меню шестерёнки → «Установить дополнение из файла». Подробности: [подпись и распространение Mozilla](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/).

Сетевое обращение `web-ext sign` к Mozilla относится к подписи, а не к работе расширения. Запросы самого браузера, обновления браузера и инструментов также не являются трафиком Local Blocklist.

Для приватных окон: `about:addons` → Local Blocklist → разрешить запуск в приватных окнах. Правила и host permissions тоже должны быть настроены. `storage.local` общий для обычных и приватных окон Firefox; история блокировок не ведётся. Проверьте приватный сценарий отдельно.

## Установка Safari на Mac

Нужны Mac, полный Xcode (для iOS 18 — Xcode 16+ с соответствующим SDK/runtime) и выбранный developer directory. При необходимости выполните `xcode-select --switch /Applications/Xcode.app/Contents/Developer`. Принятие лицензии, загрузка SDK и подпись выполняются средствами Apple на вашем Mac.

```bash
npm ci
npm run check
LB_BUNDLE_ID=local.yourname.localblocklist npm run safari:generate
```

Скрипт вызывает `xcrun safari-web-extension-converter` (либо новое имя `safari-web-extension-packager`) с `--macos-only` и `--ios-only`, `--swift`, `--copy-resources`, `--no-open`, `--no-prompt`. Это **реальный официальный конвертер**, а не вручную выдуманный `.pbxproj`. Он создаёт минимальные containing apps и extension targets в `build/apple/macos/` и `build/apple/ios/`. Проверьте все предупреждения конвертера. [Путь упаковки Apple](https://developer.apple.com/documentation/safariservices/packaging-a-web-extension-for-safari).

Повторная генерация не перезаписывает существующие проекты. Для новой генерации задайте новый `LB_APPLE_DIR`, например `build/apple-v2`, либо сохраните свои настройки подписи и перенесите ресурсы в существующий проект через Xcode. Проекты содержат **копии** `dist/safari`: одна пересборка JavaScript сама по себе не обновляет эти копии.

Откройте сгенерированный macOS `.xcodeproj`, выберите **containing app scheme**, настройте Signing & Capabilities для приложения и расширения, выполните Run. Для CLI сначала получите реальные имена схем:

```bash
npm run safari:build -- macos
# Скрипт напечатает xcodebuild -list и попросит выбрать схему.
LB_SCHEME='имя схемы из списка' npm run safari:build -- macos
# С подписью и, при необходимости, загрузкой provisioning profiles:
LB_SCHEME='имя схемы' LB_TEAM='ваш Team ID' LB_ALLOW_PROVISIONING=1 npm run safari:build -- macos
```

Без `LB_TEAM` скрипт собирает с `CODE_SIGNING_ALLOWED=NO`. Для такой development-сборки Safari Settings → Advanced → Show features for web developers → Developer → Allow unsigned extensions, затем Extensions → включить Local Blocklist. Разрешение unsigned сбрасывается при выходе из Safari. Это не постоянная подписанная установка. [Запуск Safari Web Extension](https://developer.apple.com/documentation/safariservices/running-your-safari-web-extension).

Для распространения используйте подписанное приложение через Apple Developer Program/App Store. В Safari 18.4+ на macOS Apple также поддерживает Developer ID + notarization; это **не путь для Safari 18.0 или iOS**. [Изменение Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/). Архивирование и экспорт выполняйте в Organizer Xcode с вашим профилем подписи; этот проект не содержит чужих сертификатов и provisioning profiles.

В Safari Settings → Extensions включите расширение для нужного профиля и отдельно для Private Browsing. Наличие разрешения сайта и включение в приватном режиме — разные настройки. У Safari профили имеют отдельные хранилища расширения; при необходимости импортируйте JSON в каждом профиле. [Модель профилей и приватности WebKit](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/).

## Установка Safari на iPhone / iOS 18

На ПК подготовьте исходники/архив и `dist/safari`; затем перенесите проект на Mac. ZIP ресурсов нельзя установить как iPhone-приложение.

1. На Mac запустите `safari:generate`, откройте сгенерированный **iOS** проект. Для симулятора выберите iPhone с iOS 18 и выполните Run. CLI: `LB_SCHEME='реальная схема' npm run safari:build -- ios`.
2. Для настоящего iPhone выберите Team и уникальный bundle identifier у обоих targets, подключите устройство, настройте доверие/Developer Mode, выберите устройство и выполните Run. Device-сборка требует подписи и provisioning; unsigned simulator build на телефон не устанавливается. Следуйте условиям [Apple для тестирования и распространения](https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension); не рассчитывайте на бессрочную работу development-профиля или бесплатного аккаунта.
3. Для CLI device-сборки задайте `LB_DESTINATION='generic/platform=iOS'`, `LB_TEAM`, `LB_SCHEME`; для установки используйте Xcode Run на конкретном устройстве. `safari:build` только собирает приложение и не выдаёт себя за установщик.
4. На iOS 18 откройте Settings → Apps → Safari → Extensions → Local Blocklist → Allow Extension. Также включите расширение в нужном профиле и Allow in Private Browsing, если используете приватные вкладки. Названия пунктов зависят от языка ОС.
5. В Safari откройте меню страницы → Extensions → Local Blocklist. Значок расширения открывает страницу настроек. Добавьте правило. Разрешите доступ **только к этому сайту**, если Safari показывает запрос/значок ожидания доступа, затем нажмите «Перепроверить защиту».
6. Пройдите [чек-лист Mac/iPhone](docs/SAFARI-CHECKLIST.md), включая сворачивание Safari, перезапуск и приватные вкладки. Simulator/Playwright WebKit не заменяют эту проверку.

Для распространения на iPhone нужны подписанные Apple-пакеты: development на вашем устройстве, предусмотренное Apple ad-hoc/test distribution или TestFlight/App Store. Сроки действия определяются вашим аккаунтом и provisioning profile. [Официальная инструкция запуска на iOS](https://developer.apple.com/documentation/safariservices/running-your-safari-web-extension).

## Правила и точная семантика

В настройках заполните домен, выберите тип, при необходимости задайте путь. Необязательное название — только подпись для вас. После сохранения проверьте состояние доступа, сети и защиты внутри страниц. При редактировании ID сохраняется. Удаление не имеет скрытого быстрого обхода или временного разрешения.

Для примеров ниже используется исключительно синтетический `focus.test`. Этот домен и пути **не включаются в начальный список, production-разрешения или runtime-код**.

| Настройка | Поведение |
| --- | --- |
| Весь сайт, `focus.test` | все HTTP/HTTPS пути этого hostname на любом порту |
| Поддомены выключены | только `focus.test`; `a.focus.test` не совпадает |
| Поддомены включены | сам домен и любой hostname с границей `.focus.test`; `evilfocus.test`, `focus.test.evil.test` не совпадают |
| Раздел `/section` | `/section`, `/section/`, `/section/item`; не `/section-example` |
| Раздел `/` | все пути домена |
| Точная страница `/page` | только `/page`; **`/page/` отличается** |
| Точная страница `/page/` | только `/page/`; вложенные пути не совпадают |
| `?query` и `#fragment` | игнорируются; правила не могут содержать эти части |
| Протокол | только HTTP и HTTPS; `file:`, `about:`, `data:`, `blob:`, FTP не блокируются |

Нормализация:

- Домен обрезается по краям, приводится URL-парсером к нижнему регистру и Punycode. Вводится hostname без схемы, порта, пути, wildcard и DNS-точки в конце. Разрешён канонический IPv4 и одноуровневый hostname; IPv6 в этой версии не принимается. У IPv4 нельзя включить поддомены. Неоднозначные сокращённые/hex/octal IP отклоняются.
- Конечная DNS-точка в URL **значима**: `focus.test.` не совпадает с `focus.test`. Это сознательная граница версии 1, а не защита от намеренного обхода через эквивалентные имена DNS. Псевдонимы, другие домены того же сервиса и IP тоже требуют отдельных правил.
- Путь чувствителен к регистру: `/Section` отличается от `/section`. Unicode кодируется стандартным URL-парсером в UTF-8 `%XX`; NFC/NFD не склеиваются. `%XX` нормализуется только по регистру hex-цифр. `%2f` и `%2F` эквивалентны; `%2F` и `/`, `%61` и `a` — **различны**. Семантическое декодирование пути сервером не угадывается.
- `.` и `..`, в том числе percent-encoded dot segments, разрешаются URL-парсером до сопоставления. Повторные `/` внутри/в начале пути сохраняются. У раздела завершающие `/` удаляются (кроме корня); у точной страницы сохраняются. Raw пробелы, обратные слеши, управляющие знаки и ошибочные `%XX` при вводе правила отклоняются; пробел задавайте как `%20`.
- Длина нормализованного пути — до 256 ASCII-символов, название — до 100, ID — 1–80 символов `[A-Za-z0-9_-]`; до 100 правил, импорт до 128 КиБ. Лимит намеренно ниже DNR-квот. Фактическая поддержка каждого сгенерированного выражения проверяется браузером.
- При нескольких совпадениях в объяснении используется первое подходящее правило в порядке списка. Сетевые действия одинаковы: блокировать документ. Название не меняет техническое сопоставление.

Форма «Проверить адрес» не открывает URL и не делает сетевой запрос. Она показывает совпадение списка и отдельно подтверждённые сетевой/страничный слои. Это проверка политики, а не доказательство состояния конкретной вкладки. Редактирование/тестовые URL не записываются в историю расширения.

## Импорт, экспорт, хранение

Экспорт — JSON с `schemaVersion: 2` и `rules`. ID сохраняются. Скачайте файл или скопируйте текст из поля экспорта (в том числе если Safari иначе обрабатывает скачивание). Минимальная конфигурация:

```json
{"schemaVersion": 2, "rules": []}
```

Полный пример **только для тестирования**, не начальная конфигурация:

```json
{
  "schemaVersion": 2,
  "rules": [
    {
      "id": "my-stable-id",
      "name": "Мой раздел",
      "domain": "focus.test",
      "includeSubdomains": false,
      "kind": "section",
      "path": "/section"
    }
  ]
}
```

`kind`: `site`, `section`, `exact`. У `site` поле `path` отсутствует. Импорт сначала полностью валидируется, нормализуется и показывается в JSON-превью. Неизвестные поля, повторные ID, неизвестные версии и превышения лимитов отклоняются. Только кнопка «Заменить список» применяет результат. Это замена, не слияние; предварительно экспортируйте прежний список. Новые разрешения при импорте не запрашиваются массово: выдайте их по отдельности кнопками в строках правил.

Схема 1 поддерживается как миграция: та же форма правил со стабильными ID, но отсутствующий `includeSubdomains` означает `false`. При чтении локального хранилища или импорте она преобразуется в схему 2 и сохраняется. Неизвестную/повреждённую сохранённую конфигурацию расширение не затирает пустым списком.

В `storage.local`: `policy` — единственная политика, `revision` — защита от одновременных правок, `protectionEpoch` — случайный сигнал перепроверки работающим скриптам. Ни один ключ не содержит истории посещений, счётчиков блокировок или полных тестовых/заблокированных URL. Экспорт не содержит служебных ключей. При конфликте двух окон редактора обновите настройки и повторите изменение. На диске конфигурация не шифруется самим расширением.

## Архитектура и поведение

```text
src/core/policy.ts    схема, миграция, валидация, нормализация, чистый matcher
src/core/network.ts   та же политика → переносимые DNR block-правила
src/runtime/         storage.local, очередь операций, разрешения и reconciliation
src/background.ts    непостоянная event page, синхронная регистрация слушателей
src/history.ts       маленький MAIN-world сигнал после pushState/replaceState
src/guard.ts         ISOLATED guard: проверка адреса, capture-ссылки, остановка
src/ui/              настройки и локальная страница блокировки
scripts/             сборка, аудит, упаковка, Firefox-тест, Apple-автоматизация
```

Из сохранённой конфигурации фон заново выводит политику при загрузке, `onInstalled`, `onStartup`, изменении разрешений и ручной перепроверке. Постоянно работающий фон не предполагается. Конфигурация сначала сохраняется, затем производные слои применяются; ошибки не откатывают пользовательский список молча. Интерфейс показывает желаемый список и фактическое подтверждение каждого слоя. При DNR-ошибке старые динамические правила могут сохраниться — отображается предупреждение, повторите применение. Это не распределённая атомарная транзакция между storage, DNR и scripting.

Сеть использует только `declarativeNetRequest.updateDynamicRules`, action `block`, типы `main_frame`/`sub_frame`, `regexFilter`, явную чувствительность к регистру. Проверяется `isRegexSupported`, квота при доступности константы и чтение применённых правил. В JavaScript не передаётся содержимое сетевых запросов. `webRequest`, перехват видео, изображений, XHR/fetch и изменение общих сетевых API сайтов отсутствуют. Прямая навигация, внешняя ссылка и новая вкладка могут показать штатную ошибку блокировки браузера. Это ожидаемо; сетевых redirect-правил и web-accessible resources нет. [DNR Mozilla](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/declarativeNetRequest), [DNR Apple](https://developer.apple.com/documentation/safariservices/blocking-content-with-your-safari-web-extension).

Для разрешённых доменов фон регистрирует два `document_start` скрипта на **всём домене**, включая разрешённые пути. MAIN-скрипт оборачивает только `history.pushState/replaceState`; не получает конфигурацию, URL, секреты или extension API. Отправляет событие без данных. ISOLATED-скрипт перепроверяет собственный `location.href`: события страницы не считаются доказательством совпадения. Регистрация world/persistence поддерживается Safari 16.4+, то есть входит в iOS 18. [Описание RegisteredContentScript](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/scripting/RegisteredContentScript).

Guard также проверяет capture-click, `popstate`, `hashchange`, `pageshow`, `focus`, `visibilitychange` и резервно адрес раз в 750 мс в видимой/3000 мс в скрытой странице. Он не делает DOM-сканирование на каждом тике и не зависит от MutationObserver/селекторов сайтов. Повторное внедрение обновляет существующий guard, не накапливая таймеры/обработчики. При отзыве доступа его политика очищается и таймер выключается. Лёгкая MAIN-обёртка и неактивные обработчики уже открытого документа исчезнут при его перезагрузке.

При совпадении guard вызывает `pause()`/mute доступных audio/video (включая открытые shadow roots), выгружает iframe-проигрыватели, останавливает загрузку документа, заменяет содержимое экраном блокировки. Для верхнего документа фон повторно проверяет политику, разрешение, текущий адрес вкладки и источник сообщения, затем открывает локальный `blocked.html#rule-id`. Полный URL в адрес страницы блокировки не передаётся. Для вложенного frame используется локальный экран внутри него; разрешённая родительская страница не заменяется целиком.

Изменение списка/разрешений обновляет динамические правила и регистрации и отправляет сигнал уже работающим guards. После установки расширения или добавления нового сайта **перезагрузите открытые вкладки этого сайта**, чтобы браузер запустил зарегистрированные `document_start` скрипты. Загрузка и сохранение настроек не вызывают `executeScript`: зависание внедрения в отдельную вкладку не должно блокировать список правил. Статус «скрипты зарегистрированы» подтверждает регистрацию для загрузки документов, а не наличие скрипта в каждой уже открытой вкладке.

`webNavigation` не используется: Safari не поддерживает, в частности, `onHistoryStateUpdated`. Вместо дополнительного широкого permission применены page-world сигнал, lifecycle-события и ограниченный fallback. [Матрица API и ссылки](docs/COMPATIBILITY.md).

## Разрешения и приватность

| Permission | Зачем |
| --- | --- |
| `storage` | только `storage.local`: правила и служебная ревизия |
| `scripting` | динамический document_start guard и MAIN-сигнал только на выданных доменах; новые сайты начинают работать после перезагрузки их вкладок |
| `declarativeNetRequestWithHostAccess` | блокировка документов в пределах host access без доступа к содержимому запросов |
| optional HTTP/HTTPS host permissions | доступ к страницам доменов из пользовательского списка; необходим для SPA-guard и этой модели DNR |

В manifest нет обязательных host permissions и статических content scripts. Диапазоны `http://*/*`, `https://*/*` в **optional_host_permissions** позволяют запросить любой будущий пользовательский домен. Они **не выдаются при установке и никогда не передаются целиком в permissions.request**. Фактический запрос — только HTTP/HTTPS данного hostname, либо `*.hostname`, если пользователь включил поддомены. WebExtensions host permissions не умеют ограничивать доступ только путём; для раздела нужен доступ ко всему домену, что явно объясняется формой.

В Safari запрос может потребовать ещё одного действия в меню расширений на сайте или Safari Settings → Extensions → Websites → Allow. Пользователь может выбрать временный доступ; после его истечения защита перестанет быть полной. Проверяйте отображаемое состояние. Выбор «все сайты» расширению не нужен. Возможны особенности интерфейса Safari с широким optional-диапазоном, включая лишние предложения доступа браузера; [известный отчёт WebKit](https://bugs.webkit.org/show_bug.cgi?id=290508). Наш код регистрирует скрипты только по правилам и проверенному доступу, даже если пользователь вручную выдаст более широкое разрешение.

При успешном изменении списка удаляются больше не нужные grants, где API это позволяет. Перекрывающий wildcard сохраняется, пока его отзыв затронул бы другое правило. Например, при сужении родительского wildcard до дочернего домена может потребоваться вручную отозвать старый доступ и снова выдать узкий. Лишний доступ отмечается в настройках. Пассивная обработка `permissions.onAdded` не удаляет только что выданный доступ до сохранения нового правила.

Нет permissions `tabs`, `history`, `cookies`, `webRequest`, `nativeMessaging`, `downloads`, `unlimitedStorage`, `webNavigation` или `activeTab`. API `tabs.query/get/update` используются в рамках host permissions; широкого чтения URL всех вкладок нет. Диагностика хранится только в памяти фона и показывает общие ошибки без полных URL. Адрес текущей страницы/клика проходит между изолированным скриптом и фоном локально для проверки, не сохраняется и не отправляется внешнему сервису. Включаемого расширенного логирования нет.

Ни аналитики, ни crash reporting, ни CDN, ни удалённого кода, ни внешних сетевых запросов нашего runtime-кода. `storage.sync` не используется. JSON-экспорт вы сохраняете самостоятельно; он раскрывает ваш список тому, кому вы его передадите.

Host permissions **не являются запретом исходящих соединений**. CSP с `connect-src 'none'`, `default-src 'none'` ограничивает extension pages дополнительно; она не является firewall, не управляет сетью посещаемых сайтов, не заменяет проверку кода и не охватывает инструменты npm/подписи или код страницы в MAIN world. Сайты могут продолжать свои обычные сетевые запросы в разрешённых разделах.

## Отладка, обновление и удаление

Firefox: `about:debugging` → Inspect расширения; проверяйте `browser.storage.local.get()`, `browser.declarativeNetRequest.getDynamicRules()`, `browser.scripting.getRegisteredContentScripts()`, `browser.permissions.getAll()`. Не публикуйте полученный список правил или адреса из консоли. Кнопка «Перепроверить защиту» повторяет применение и проверку. Safari: Develop/Web Extension Background Pages и инспектор страницы; на iPhone включите Web Inspector и подключите устройство к Mac. [Документация Apple по отладке](https://developer.apple.com/documentation/safariservices/troubleshooting-your-safari-web-extension).

При обновлении экспортируйте список, увеличьте `package.json` version, выполните `npm ci`, проверки и сборку. Firefox: сохраните ID, подпишите новую версию, установите её поверх старой. Safari: обновите копии ресурсов в проектах, увеличьте версии app/extension targets, подпишите и установите новую сборку. Правила остаются в local storage соответствующего расширения/профиля, поддерживаемая схема мигрирует. После обновления расширения перезагрузите старые вкладки: уже внедрённый код не может быть полностью выгружен браузерным API.

Для удаления достаточно обычного удаления расширения в Firefox или содержащего Safari-приложения средствами ОС. Экспортируйте список заранее. При необходимости очистите данные расширения штатными средствами браузера/приложения. Нет антиудаления, скрытых служб, блокировки настроек или влияния на другие приложения. Перезагрузите открытые страницы, чтобы убрать старый внедрённый guard; DNR и регистрации принадлежат расширению и удаляются браузером вместе с ним.

## Известные границы

- Не обещается отсутствие первого кадра: асинхронная загрузка политики, восстановление документа, ограничения CSP MAIN world, заморозка фоновых вкладок и изменение history-методов страницей могут задержать guard. DNR закрывает сетевую загрузку совпадающих документов; при SPA без запроса остаётся событийная и резервная проверка. Фоновые/iOS таймеры могут быть сильно отложены браузером.
- Это инструмент самоконтроля, не защита от враждебной страницы или пользователя, намеренно обходящего расширение. Страница может испортить MAIN hook; другие DNS-имена, конечная точка hostname, зеркала, иной путь, percent-encoding серверного алиаса, другие браузеры и отключение расширения не предотвращаются.
- Shadow DOM, закрытые проигрыватели, WebAudio и чужие фреймы нельзя универсально остановить через media API. Уход верхнего документа обычно прекращает его контекст, но мгновенная остановка любого внешнего/системного воспроизведения не гарантируется. Для iframe guard не выполняет привилегированное перенаправление верхней вкладки.
- Browser-reserved страницы, магазины расширений и защищённые браузером домены могут быть недоступны scripting. Там возможно только доступное браузеру сетевое поведение; ошибка перепроверки отображается. Не рассматривайте строку «активно» как обход браузерных ограничений или гарантию для чужого профиля.
- Конфигурация намеренно ограничена 100 правилами; нет пользовательских regex, распознавания контента и быстрых исключений. DNS aliases/IPv6 и домены с конечной точкой не объединяются.
- macOS/iPhone, настоящая BFCache, native permission UI, долговременная установка/подпись, stop/playback и реальное оформление на 320/768/1024/1440 px требуют [проверки на устройствах](docs/SAFARI-CHECKLIST.md). Наличие теста или скрипта автоматизации не означает, что он был выполнен в Safari.
